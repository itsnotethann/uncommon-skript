# uncommon-skript

Skript's platform-independent core, split out so it can run somewhere other than Bukkit.

A fork of [skript-minestom](https://github.com/skript-minestom/skript-minestom), which is itself a
fork of [Skript](https://github.com/SkriptLang/Skript). Only `common/` and `domain/` are built here.

## What's different from upstream

Upstream's `common/` threads `org.bukkit.event.Event` through ~150 files and calls Bukkit directly
for scheduling, addon lifecycle, logging and server state. That is replaced here by a platform SPI:

- `org.skriptlang.skript.lang.event` — `PlatformEvent`, `Cancellable`, `EventPriority`
- `org.skriptlang.skript.platform` — `EventBus`, `EventChannel`, `PlatformScheduler`,
  `AddonHandle`, `AddonRegistry`, `PlatformEnvironment`, `LogSink`

There is no Bukkit implementation and no `org.bukkit.*` compatibility shim. Both existed here
until they were removed; see *Bukkit addons* below for why.

Two upstream defects were fixed along the way, both independent of the SPI:

- event handlers dispatched in reverse priority order, so `MONITOR` ran first and observed state
  before the handlers it exists to observe
- parse warnings logged at `INFO`, making them invisible to anyone filtering at `WARN`

## Layout

| Path | Built | |
|---|---|---|
| `spi/` | yes | the platform interfaces. 18 files, no dependency on the rest of Skript |
| `common/` | yes | the platform-free core; a tracking fork of upstream's `common/` |
| `domain/` | yes | fork-owned domain interfaces under `org.skriptlang.skript.domain`; no upstream occupant |
| `minestom/` | no | inert. Present only so merges from upstream never hit modify/delete conflicts. Do not edit it here |

`settings.gradle.kts` includes `spi`, `common` and `domain` only, which is what makes `minestom/`
inert. `spi` is transitive through `common`, so consumers get it for free.

## Bukkit addons

They do not work, and this fork no longer pretends otherwise.

The shim was built so a Bukkit-compiled addon jar would class-load, on the reasoning that the JVM
resolves method signatures lazily — which is true, and turned out not to be enough. A Skript addon
does not merely call Skript, it *implements* Skript's syntax interfaces. `Expression.getArray` is
`getArray(PlatformEvent)` here and `getArray(org.bukkit.event.Event)` upstream; different erasure
means the addon's method is not an override at all, so the abstract method is never implemented.
Tested against skript-reflect 2.6.3: it loads, enables and registers its syntax, then throws
`AbstractMethodError` the first time a syntax element is evaluated.

Making that work means either reflective bridges on the hottest path in Skript, or bytecode
rewriting at addon load time. Neither is worth it for a fork whose point is the retype, so the
shim, the Bukkit adapters and the Plugin-typed addon API are gone. `AddonRegistry.load` in the SPI
is the seam a host would implement to add a native addon mechanism; nothing implements it yet.

## Using it

```
com.github.itsnotethann.uncommonskript:common:1.0.0-alpha.1
com.github.itsnotethann.uncommonskript:domain:1.0.0-alpha.1
```

Or as a composite build, which is how skript-minestom consumes it:

```kotlin
includeBuild("../uncommon-skript")
```

## Fork point

`upstream-base` tags the last commit shared with upstream. Everything after it is the fork delta:

```
git diff upstream-base..main -- common/src/main/java
```

Most of that diff is mechanical retyping of the event type and is regenerated by script rather
than by hand; a much smaller set of files carry real logic changes. The only `org.bukkit` left in
`common/` is a string literal in `classExists`, used for platform detection.
